## What happened

`krill-pi4j` had a PWM/duty-cycle API but nothing that spoke in the units a servo
actually needs — angle or microseconds, never duty-percent (percent can't carry the
resolution a servo needs at 50 Hz). This was filed as a `dev-task` with a full API
shape and an explicit composition order attached, not a reproduction. The order is
worth a lessons entry because two of its steps are easy to get backwards, and getting
them backwards doesn't throw — it just quietly moves the servo to the wrong angle or
lets it grind against a mechanical stop.

## Fix

Added `com.krillforge.pi4j.servo` to `krill-pi4j`:

- `ServoProfile` — per-unit calibration (`pulseMinUs`/`pulseMaxUs`, `angleMinDeg`/
  `angleMaxDeg`, `reversed`, `trimDeg`) and the mechanism's safety envelope
  (`limitMinDeg`/`limitMaxDeg`, `endStopBackoffDeg`, `maxRateDegPerSec`). Validates its
  own invariants in `init {}` (min < max, positive rate, backoff leaves travel) so a bad
  profile fails at construction, not on first use.
- `ServoMath` — the pure composition, no hardware, no coroutines: reverse, then trim,
  then clamp to the effective limit window, then rate-limit, then map to a pulse width.
  **Reverse before trim**: trim is "this individual unit's zero is off by N degrees" in
  the operator's frame; applying it before reverse would silently negate every trim
  value the next time `reversed` gets flipped. **Trim before limits**: trim describes
  the unit, limits protect the mechanism — limiting first would let a trimmed request
  sail straight past the physical stop the limit exists to prevent. Both orderings are
  pinned by dedicated tests (`ServoMathTest`), including one named for the trap
  directly: trim cannot push a joint past its software limit.
- `PulseServo` — the `Servo` implementation. `pulse(us)` converts to an angle and
  re-enters the pipeline at the clamp step; there's deliberately no bypass, so a raw
  pulse can't be used to sidestep the mechanism's limits. Every command returns a
  `ServoCommandResult` (`Applied`/`Clamped`/`RateLimited`/`Disarmed`/`Rejected`) as a
  value rather than a log line, so a caller can react to "my target is out of reach"
  instead of a clamp happening silently underneath it.
- `Pca9685ServoBank` — a `ServoBank` over one PCA9685: every servo's pulse write lands
  in a staging array, and `setAngles()` flushes the whole array with one
  `Pca9685Client.writeFrame` block write, so a batch of channel updates can't tear
  across separate I2C transactions. `startWatchdog()` torques off every channel if no
  update arrives inside the window — tested with `kotlinx-coroutines-test` virtual time
  (`advanceTimeBy` + `backgroundScope`), not a real `delay()`.

## Prevention

When an API's spec calls out an explicit ordering between steps that individually look
commutative (reverse/trim/limits all "just add or clamp a number"), write one test per
adjacent pair proving the order matters, not just one test per step in isolation. A
step-only test suite would have passed with trim and limits swapped; the ordering test
is what actually pins the design decision described in the issue.
