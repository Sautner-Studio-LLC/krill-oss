## What happened

`krill-pi4j` had no support for the PCA9685, the default answer once a Pi's four
hardware PWM channels run out (servo HATs, LED drivers, ESC banks). This wasn't a bug
in existing code — it's a missing capability, filed as a `dev-task` with a full
register-level spec attached rather than a reproduction. What made it worth a lessons
entry anyway is that the spec called out four traps in the PCA9685 datasheet that each
produce a **silent wrong result** — no exception, no error field, just quietly broken
hardware behavior — which is exactly the class of bug this driver needed to be built to
avoid from day one, not patch in after the fact.

## Fix

Added `com.krillforge.pi4j.pca9685` to `krill-pi4j` (the client lib, not a new daemon
service — `WriteBytes(bus, address, register, bytes)` with MODE1's auto-increment bit
already lets one 64-byte I2C transaction set all 16 channels, so no proto change was
needed):

- `I2cBus` / `I2cClientBus` — a narrow register-level interface the driver is written
  against instead of the gRPC `I2cClient` directly, so the sleep/prescale dance and the
  frame-write byte layout are asserted exactly in tests against a fake bus (no daemon,
  no gRPC, no hardware).
- `Pca9685Registers` — register map and `prescaleFor(targetHz, oscillatorHz)`, with
  `oscillatorHz` an explicit parameter rather than a hardcoded 25 MHz: real parts
  measure 23–27 MHz, so every pulse-width conversion is wrong by that percentage until
  a board is calibrated against a scope.
- `Pca9685Client.setFrequency` — **PRE_SCALE is only writable while MODE1.SLEEP=1.**
  Writing it any other time succeeds silently and does nothing; the sequence has to
  sleep, write, wake, wait ≥500µs for the oscillator, set RESTART, then **read
  PRE_SCALE back and reject the call if it doesn't match** rather than trusting the
  write completed.
- `Pca9685Client.writeFrame` — stripes the ON edge across the cycle
  (`on_n = n * 4096/16`) instead of starting every channel at count 0, so 16 channels
  don't switch on the same edge and brown out the supply rail; `isAsleep()` exposes
  MODE1.SLEEP so a caller can poll for the chip's other silent failure — a brownout
  reset returns MODE1 to its power-on value with no error and no output, ever.
- `Pca9685Board` — composes the chip driver with its OE (output-enable) pin as one
  object, because you can't safely reason about one without the other. OE is
  active-LOW (`LOW = armed`, `HIGH = disarmed`), so **the fault action is OE HIGH** —
  any doc or API describing "assert OE low to disable" has the polarity backwards and
  would arm the outputs on a fault. The LOW→armed mapping is pulled into a standalone
  `isOeLow(state)` function specifically so this direction is unit-tested without a
  live GPIO.

## Prevention

When a hardware datasheet documents a "write succeeds, nothing happens" failure mode
(a register gated on a mode bit, a broadcast/all-call address, an active-low enable
pin), treat each one as a required unit test, not a comment. This driver's tests
(`Pca9685ClientTest`, `Pca9685BoardTest`) assert the exact register byte sequence for
init and the sleep dance, that a bad PRE_SCALE read-back throws instead of silently
succeeding, and that the OE polarity function maps the correct direction — all against
a fake `I2cBus`, so the regression is caught in CI before it reaches a chip that goes
dark with no error at all.
